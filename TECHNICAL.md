## Core Problem

In the vanilla engine, Critical Damage lives in a **single shared field**
on the player struct (`playerStruct + 0x890`). Both primary and secondary
read from that same location, which makes a naive CD boost leak to whichever
weapon is swinging.

The mod solves this by hooking the exact instruction the engine uses to
store the currently equipped possessed weapon. From there it can read the
weapon pointer directly and apply the boost only while that weapon is
equipped.

## The Equip Hook

The instruction at `Darksiders2.exe+0x493914` is:

```asm
mov [rdi+0x370], rbx    ; 48 89 9F 70 03 00 00
Registers at this site:

rdi = container object (a per-inventory-item wrapper; not playerStruct)

rbx = pointer to the possessed weapon being equipped

A parallel instruction at +0x493C49 (and qword ptr [rbx+0x370], 0) clears
the same field when a non-possessed weapon is equipped. Both are part of a
std::shared_ptr<PossessedWeapon> assignment generated by MSVC.

Hook strategy
The mod installs an inline ASM shellcode on +0x493914 that:

Pushes rax, rbx, rcx, rdx, flags.

Saves rbx (the weapon pointer) to a global.

Saves rdi (the container) to a global.

Increments a monotonic sequence counter.

Pops the saved registers.

Jumps to the MinHook trampoline (which executes the original mov).

Then a 60 Hz thread:

Detects new SET events via the sequence counter.

Verifies the pointer is a possessed weapon (rarity == 5 at +0x308).

Reads [container+0x370] every tick to get the live state. If the field
was zeroed (weapon unequipped) or replaced (different weapon equipped),
the thread stops boosting.

Reading the live field each tick instead of trusting CLEAR events is what
makes item equips transparent: when you equip armor, the engine does a
CLEAR + re-SET on the same container in rapid succession, and the live field
simply ends up with the same value.

Why a Shellcode Hook for the Equip Write?
The instruction at +0x493914 is a write (mov [rdi+0x370], rbx). We need
rbx (the weapon pointer) before the write executes.

Three approaches were tried:

MinHook with a C++ function — doesn't expose registers before the
prologue cleanly.

Raw byte patch — fragile, thread-unsafe.

MinHook with inline shellcode — chosen. MinHook handles thread
suspension internally, and the shellcode preserves all registers we
touch (rax, rbx, rcx, rdx, flags).

Known Limitations
Character Stats panel
The panel reads playerStruct + 0x890 once per UI frame. The mod writes to
that field at 60 Hz, so the panel can display a value one frame stale. The
weapon tooltip (inventory bottom-left) and combat damage are always correct.

Steam / classic versions
Offsets are for the Epic Games Deathinitive Edition build.

Steam Deathinitive — expected to work (same binary revision), untested.

Classic (non-Definitive) — different binary, will not work.

Building from Source

to .asi. Place it in the game root next to dxgi.dll.

Development History
The equip hook was discovered via Cheat Engine:

"Find out what writes to playerStruct + 0xD7C" during equip revealed
+0x45497A — but the disassembly showed it was Scaleform UI code iterating
over all equipped weapons, not the actual equip logic.

Scanning for a stable weapon pointer found multiple writes at container
+0x370 — both the SET (+0x493914) and CLEAR (+0x493C49) sites.

Extracting the field name from the disassembly (shared_ptr pattern)
confirmed the semantics: the engine stores the equipped possessed weapon
here as part of an assignment chain.

The final mod relies only on the SET hook plus a live read of the field,
which is 100% deterministic and requires no heuristics.
